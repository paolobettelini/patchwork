# patchwork-database

## Data model

### `accounts`

- `uuid`: canonical hyphenated UUID string, primary key.
- `nickname`: required, unique, at most 16 characters.
- `email`: required and unique; the library trims and lowercases it.
- `password_hash`: optional Argon2 hash of the client-side password digest.
- `created_at`: generated by the database.

Session tokens, OAuth codes and app access tokens are stored in dedicated
tables as SHA-256 hashes rather than in `accounts`.

### `pending_registrations`

- Holds normalized email/nickname and an Argon2 password hash until email is verified.
- Stores only SHA-256 hashes of the random verification ID and six-digit code binding.
- Enforces one active row per email/nickname, expiration, and a failed-attempt counter.
- Is consumed before the UUID-backed account is created.

### `github_accounts`

- `account_uuid`: Patchwork account primary/foreign key.
- `github_user_id`: authoritative numeric GitHub user ID with a unique constraint.
- `github_login` and `github_avatar_url`: cached display metadata.
- `linked_at` and `updated_at`: association timestamps.

### `github_oauth_states`

Stores hashed, short-lived and single-use state values for the GitHub callback.
The callback recovers the Patchwork UUID from this table and does not rely on a
browser cookie surviving the external redirect. Each row also stores the
validated completion URL selected when the flow starts, allowing web and
desktop clients to return to different destinations without trusting callback
query parameters.

### Registry tables

- `repositories` identifies GitHub repositories by numeric GitHub ID and caches
  mutable owner/name/URL display coordinates.
- `mods` is the permanent globally unique slug, publisher, repository, Rescan
  base path, latest-version pointer, and download count.
- `mod_versions` stores one immutable semantic version with exact commit,
  directory Git tree OID, manifest blob/SHA-256, optional README/image
  coordinates, metadata, and publishing identities.
- `mod_version_dependencies` stores ordered `init`, `run`, and `ownership`
  relations per version, with typed `mod` or `modpack` targets.
- `modpacks` is the permanent modpack identity with publisher, repository,
  Rescan base path, latest-version pointer, and downloads.
- `modpack_versions` stores immutable semantic versions with exact Git
  snapshot, manifest, README/image, metadata, and publisher coordinates.
- `modpack_version_dependencies` stores ordered `mod`, `modpack`, and `ignore`
  relations per immutable version with typed targets.
- `registry_scans` and `registry_scan_entries` persist short-lived authoritative
  previews. Publish accepts entry UUIDs and reads all metadata from these rows.

`UNIQUE(mod_id, version)` and `UNIQUE(modpack_id, version)` prevent an existing
release from being replaced by different source, including under concurrent
publish requests. Missing dependency targets are retained as warnings and can
be published later; graph resolution remains responsible for cycle detection.

## README handling

README coordinates consist of numeric/canonical repository identity, exact
`source_commit`, `repository_path`, `readme_path`, and `readme_blob_oid`.

When a page is requested, the web backend should fetch the Markdown at that exact commit, render it and sanitize the generated HTML. Relative images are resolved against the directory containing the README at the same commit. Therefore an image such as `screenshots/demo.png` does not need a database row.

Recommended rendering pipeline:

1. Resolve the default branch to a commit SHA during scan and store it as `source_commit`.
2. Fetch the README from GitHub using the repository, SHA and `readme_path`.
3. Convert Markdown to HTML with raw HTML disabled or aggressively sanitized.
4. Rewrite relative links and image sources to the same repository and commit.
5. Optionally cache sanitized HTML, ETag and fetch time in a separate cache table or external cache. The canonical database can continue storing only source links.
6. Apply size limits, timeouts and an image policy. Do not allow arbitrary Markdown HTML, scripts, `javascript:` URLs or unsafe SVG execution.

Pinning a commit is mandatory: storing only `main` would let displayed README
and downloaded source change after publication. The registry does not store
README/image bytes or source code.

## SQLite usage

```bash
cp .env.example .env
cargo test
cargo run --example basic
```

In an application:

```rust
use patchwork_database::{CreateAccount, Database};
use uuid::Uuid;

let database = Database::connect("patchwork.sqlite")?;
let account = database.create_account(CreateAccount {
    uuid: Uuid::new_v4(),
    nickname: "PatchworkDev".into(),
    email: "dev@example.com".into(),
    password_hash: None,
})?;
# Ok::<(), patchwork_database::DatabaseError>(())
```

`Database::connect` creates a pool and automatically runs the embedded SQLite migrations. Every SQLite connection enables foreign keys and a five-second busy timeout.

## MySQL usage

Compile without the default SQLite backend:

```bash
cargo build --no-default-features --features mysql
cargo test --no-default-features --features mysql
```

Then use a MySQL URL:

```text
mysql://patchwork:password@127.0.0.1/patchwork
```

The same `Database::connect`, models and operations are used. Backend-specific SQL is isolated in `migrations/sqlite` and `migrations/mysql`.

Only one backend feature may be enabled at a time. This keeps query types and the connection pool straightforward. Switching production to MySQL is a rebuild/configuration change, not a rewrite of the application API.

## Diesel CLI

```bash
cargo install diesel_cli --no-default-features --features sqlite
```

Generate or run SQLite migrations using the default `diesel.toml`:

```bash
DATABASE_URL=patchwork.sqlite diesel migration run
```

For MySQL

```bash
export DATABASE_URL='mysql://patchwork:password@127.0.0.1/patchwork'
diesel migration run --migration-dir migrations/mysql
```

The library embeds migrations into the binary, so normal applications do not need the CLI at runtime.

## Main API

- `create_account`, `get_account`, `get_account_by_email`
- `create_pending_registration`, `verify_pending_registration`, `delete_pending_registration`
- `create_github_oauth_state`, `consume_github_oauth_state`
- `get_github_account`, `get_github_account_by_user_id`
- `link_github_account`, `unlink_github_account`
- `get_mod`, `get_registry_mod_state`, `search_mods`, `list_mods_by_publisher`
- `get_modpack`, `get_registry_modpack_state`, `search_modpacks`, `list_modpacks_by_publisher`
- `create_registry_scan`, `get_registry_scan`, `publish_registry_scan`

All operations return `Result<T, DatabaseError>` rather than hiding failures behind `bool` or `Option`.

## Search strategy

The included indexes cover IDs, publishers, dates, repository coordinates and dependency reverse lookups. The simple search methods use `LIKE` over ID/title/description and are suitable for an initial catalogue.

For a larger catalogue, add backend-specific full-text search:

- SQLite: an FTS5 virtual table maintained by triggers.
- MySQL: a `FULLTEXT` index and `MATCH ... AGAINST`.

Keep that as a backend-specific search adapter rather than forcing incompatible full-text SQL into the common schema.

## Synchronous Diesel in an async server

Diesel's standard connections are synchronous. In Axum, Actix or another async server, call this library from a blocking worker (`spawn_blocking`, Actix `web::block`, or a dedicated database executor). Do not mark these methods `async` unless the work is actually moved off the async runtime thread.
